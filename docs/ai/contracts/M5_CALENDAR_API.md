# M5-CALENDAR-v1
30/10/2026. M4 aceptado en 7fe9bd6. M5 backend parte exactamente de ese commit; Angular parte de M3 d0b7a45, su último código aprobado. Ramas independientes codex/m5-calendar; main/turnos/M3/M4 preservados.

UI privada /calendar, con guards de plan/onboarding/consultorios y CALENDAR_ENABLED=false por defecto. Día/semana, fechas dd/MM/aaaa mediante app-date-picker, todas las sedes o una, slots M3 y reservas M4, cada tarjeta con hora local/zona IANA. La semana agrupa fechas civiles de cada sede, no convierte slots a una zona supuesta común. UTC se usa en requests; consulta de reservas amplía límites UTC dos días para cubrir cualquier sede y luego filtra por fecha local. Se consume toda la paginación, sin truncar en 100 reservas/consultorios. Sin fallback a mocks.

API M3/M4 sin rutas nuevas. Extensión aditiva: POST /bookings acepta attendeeName?:string (trim 1..160 si presente); si se omite usa contactName. Booking añade attendeeName:string, nombre administrativo de la persona atendida; contactName/contactPhone identifican al solicitante. patientId sigue opcional y propietario. Datos inmutables durante estados/reprogramación. Recibos/eventos históricos M4 sin attendeeName se interpretan como contactName; no se reescriben. Migración 0007 añade columna nullable con CHECK de longitud, sin backfill: lector COALESCE(attendee_name,contact_name). Trigger adicional protege inmutabilidad. Migraciones anteriores inmutables, catálogo final fijado desde SQL publicado; upgrade/rollback/conservación obligatorios. Sin pacientes nuevos ni cambios clínicos.

Angular excluye exactamente /bookings y subrutas del interceptor timeZone, como /clinics; conserva contexto clínico. Idempotency-Key por intento lógico, reutilizada al reintentar misma operación tras fallo de red/5xx. Doble clic bloqueado. 409 exige actualizar disponibilidad/versión antes de nueva mutación; borrador conservado. Respuestas tardías aisladas por generación de carga, propietario y editor. Derechos verificados y vigentes para acciones; downgrade bloquea altas/reprogramación pero permite estados si tiene gestión efectiva; errores refrescan capacidades sin borrar campos. Go sigue siendo autoridad. Cambio de propietario limpia datos; cambio de filtros no permite que una respuesta mutante edite otra reserva.

Sin drag-and-drop, portal público /appointments, login de staff, email, pagos o marketing. M6 no autorizado. Ensayo real aislado Supabase Auth/Gateway/Billing/PostgreSQL + Angular con flags solo en snapshot de fixture; nunca producción.
